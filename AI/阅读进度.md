## 3. 已知问题与未决项

- `grep -o` 在多文件模式下不带文件名前缀，GNU 行为一致，保持现状。
- 目录操作数缺 `-r` 时的报错文案与 GNU 措辞不同，功能对，措辞后续对齐。
- 单文件搜索的 `-c` 输出不带文件名，GNU 行为一致，保持现状。
- `ls` 的空目录返回退出码 `1`（GNU 返回 `0`），是本项目「无结果返回 1」约定的刻意取舍，已写进 README。下一个指令若也属命中类，沿用同一口径。
- `ls -l` 没有链接数、属主、属组三列，也没有 `total N` 汇总行：Windows 的 `stat` 没有属主语义也没有 `st_blocks`，不是漏做。
- `cat` 的空行判定是「内容完全为空」，含空格的行不算空行（GNU 实测如此），所以 `-s` 不压它、`-b` 照样编号。
- `cat` 的二进制判定：含 NUL 字节，或 utf-8/系统首选编码/gb18030 都严格解不出来，就算二进制，按字节原样转交。latin-1 永远能解，判定文本时必须排除它。
- `cat` 的文件打不开返回退出码 2（GNU cat 返回 1），沿用本项目「用法或运行错误返回 2」的约定，已写进 README。
- `head` 的 `+N` 与 `N` 等价，不是 tail 那种「从第 N 行开始」；`-N` 才是「除末 N 行之外全要」，且 `0` 与 `-0` 含义不同。GNU 实测如此，已写进 README。
- `head` 的乘数后缀表与 GNU 帮助文本对不上（帮助说 kB=1000，实测 k=1024、kB=1000、K=1024），实现以实测为准：`b`=512、`k`/`K`=1024、`m`/`M`=1024²、`G`=1024³、`T`=1024⁴、`P`=1024⁵、`E`=1024⁶，字母加 `B` 是 1000 进制，字母加 `iB` 等同对应的单字母形式。
- `head` 的纯数字上界按 uintmax（2^64-1），负数按 intmax（2^63-1），GNU 实测如此；`Z`/`Y` 后缀语法合法但数值算出不来，报「数值超出可表示范围」。
- `head` 的打不开的文件不打标题，目录却先打标题再报「是一个目录」，两者行为不同，与 GNU 一致。
- `head` 的 `-c` 字节数按源文件算，GBK 文本输出成 UTF-8 后字节数会变多，已写进 README。
- `tail` 的 `+N` 是起点不是等价写法：`-n 5` 取末 5 行，`-n +5` 从第 5 行开始到最后。这与 head 相反（head 的 `+N` 等价 `N`），是最容易记错的一条。
- `tail` 的负号等价于正号：`-n -5` 与 `-n 5` 同义，都是取末 5 个。`-n 0` 一个不要，`-n +0` 全部都要。
- `tail` 的乘数后缀乘的是**行数**（`-n 1b` 就是 512 行），`-c` 的后缀乘的是**字节数**；两边后缀表相同（`b`=512、`k`/`K`=1024、`kB`=1000、`KiB`=`K`），GNU 实测如此。
- `tail` 的末行没有换行符时它**也算一行**（`tail -n 2` 会把它算进去），与 head 的 `-n -1` 会把它一起去掉不同。
- `tail` 回读大文件时起点多半落在行中间，开头那截半行要丢掉，所以实现要凑够「行数+1」个分隔符才停；GNU 实测同样丢半行。
- `tail` 的编码判定取的是「将要输出的那一段」而不是文件开头，所以 GBK 日志的末尾照样出中文；这是有意比 head 更进一步的取舍，已写进 README。
- `tail` 跟随时输出必须显式 flush：输出接管道时 Python 是块缓冲（攒 8KB 才写），不刷的话 `tail -f` 跟半天什么也看不见，GNU tail 跟随时是行缓冲的。
- `tail` 的 `-F`（按文件名跟）每轮重新打开再关掉文件：Windows 上打开着的文件不能改名（没开 `FILE_SHARE_DELETE`），日志轮转第一步就是改名，长期占着句柄会直接失败。
- `tail` 的 `--pid` 在 Windows 上不能用 `os.kill(pid, 0)` 探测：那边的 0 号信号会真的把目标进程终止掉，改用 `OpenProcess` 探句柄。
- `tail` 的文件打不开返回退出码 2（GNU tail 返回 1），沿用本项目「用法或运行错误返回 2」的约定，已写进 README。
- `wc` 的列宽是**逐列**算的：每列先按自己出现过的最大计数定下限；只打印一列、且不打 total 行时不做对齐，否则每列再按「普通文件字节数之和」撑开。标准输入与目录的大小事先数不出来，GNU 为它们预留 7 列。
- `wc` 的列宽是最小宽度，计数比预留宽度长时直接写长、不截断，所以 total 行的字节数可以比前面的行更宽（GNU 实测如此：`m7.txt` + stdin 的 total 是 8 位，前面的行仍是 7 位）。
- `wc` 的词：片段里夹控制字符不算断开（`a\x01b` 是一个词），整个片段里一个可打印字符都没有时不算词（纯二进制内容词数是 0）。中文算可打印字符，所以中文文件在 GNU 的 C 区域设置下词数是 0，本实现不是。
- `wc` 的 `-m` 与 `-L` 按判定出的编码解码后统计：GBK 汉字算 1 个字符、2 个显示列；GNU 在 C 区域设置下解不出 GBK，会把字符数整个记成 0，换到 zh_CN.UTF-8 跑 GNU 数字与本实现一致。
- `wc` 的 `-L` 取行内出现过的最大显示列数（`\r` 把列号清零，之后的宽度再大也不算数），不是行尾那一处的宽度。
- `wc` 的文件打不开返回退出码 2（GNU wc 返回 1），沿用本项目「用法或运行错误返回 2」的约定，已写进 README。
- `find` 的表达式优先级是 `!` > `-a` > `-o`，相邻谓词默认按 `-a` 结合；路径必须写在表达式前面，写在后面报「路径必须写在表达式前面」。
- `find` 的隐式 `-print` 加在**整条表达式**后面（不是最后一个谓词后面），且 `-prune` 不算动作（GNU 手册明确说 `-prune` 或 `-print` 之外没有动作才补 `-print`），所以 `find . -type d -prune` 仍会打印命中的目录。
- `find` 的动作会截断同层 `and` 链：`-print` 恒为真且一旦执行就不再算右半边，这是 `-name '*.txt' -print -o -name '*.md' -print` 每个文件只打印一次的原因。
- `find` 的 `-mmin` 精确形式把「当前这一分钟」算作第 1 分钟：90 秒大的文件落在 `-mmin 2` 而不是 `-mmin 1`（GNU findutils 4.10 实测），而 `-mtime` 的天数计数没有这个偏移；`-mmin +N` / `-mmin -N` 仍是自然语义（大于 N 分钟 / 小于 N 分钟）。
- `find` 的目录大小按 0 算：Windows 的目录 `st_size` 不稳定（空目录 0、条目一多就 4096），GNU 侧恒为 0；不统一的话同一条命令的结果会随目录内容变化。
- `find` 的 `-exec` 在 Windows 上找不到可执行文件时退回 `cmd /c`，且整条命令要作为**一个**参数传过去（拆成多个参数时 cmd 会按自己的编码重拼命令行，中文路径变 GBK 字节）。
- `find` 的 `-printf` 只支持 `%T@` 不支持 `%T`：GNU findutils 4.10 的 MSYS 构建遇到单独的 `%T` 会报 `memory exhausted` 崩掉。
- `find` 的 `%T@` 小数点后印 10 位（GNU 的纳秒被算大了 10 倍），且必须用整数纳秒算（`st_mtime_ns`），浮点秒的二进制噪声会让末几位差 1。
- `find` 什么都不匹配时返回退出码 1（GNU 返回 0），沿用本项目「无结果返回 1」的约定；`-delete` 这类只做动作不打印的用法按「命中了就算有结果」返回 0。

- **产出**：w2l/commands/wc.py、tests/test_wc.py、tests/conftest.py、README.md（wc 章节）；另单独提交 AI/脚本/ 下 35 个探针与差分脚本
- **关键收获**：GNU wc 的列宽是逐列算的，不是全局一个宽度：每列先按自己出现过的最大计数定下限，只有一列且不打 total 行时完全不对齐，否则每列再按「普通文件字节数之和」撑开；标准输入与目录的大小事先数不出来，GNU 为它们预留 7 列。列宽是最小宽度，计数比预留宽度长时直接写长不截断，所以 total 行的字节数可以比前面的行更宽（9999999 字节的文件加 stdin 时 total 是 8 位、前面仍是 7 位）；只打一列且不打 total 时不撑开（-l 读 100000 字节的文件仍输出「1 file」）；词的判定是「空白分隔的片段加片段里至少有一个可打印字符」：片段里夹控制字符不算断开（a\x01b 是一个词），整个片段没有可打印字符时不算词（纯二进制词数是 0）；-L 取行内出现过的最大显示列数（\r 把列号清零、之后宽度再大也不算），制表符展开到 8 的倍数、全角字符 2 列、组合字符 0 列；行只按 \n 计，末行没有换行不算一行但词照样算；total 的最长行取最大值不是求和；重复的 - 只读一次标准输入，第二个 - 读到的是空的且 total 只算一次；目录会打一行全 0 再报错、缺文件只报错不输出计数行；用 Git Bash 的 GNU wc 做 476 组差分对照加 1600 组随机 ASCII 文本 fuzz，除 GBK 文件的 -m/-L（编码取舍，已写进 README）外逐字节一致
- **负面结果**：列宽模型一开始按「全局一个宽度」设计，差分对照 50 组不一致才暴露是逐列的；-L 一开始只取行尾那一处的宽度，带控制字符和 CRLF 的语料都算错，改成取行内出现过的最大列数才对；词的判定一开始按「非空白片段」算，纯二进制内容会算成 1 个词而 GNU 是 0，补上「片段里至少有一个可打印字符」才对；bash 工具的输出会把空格和等号吃掉，两轮探针的结论是错的（看到的「 1 f9.txt」其实是「1 f9.txt」），改成把探针结果写进文件再读才拿到可信数据；write 工具写探针脚本时路径被写坏过一次（目录名被吞、脚本落在 AI 根目录），重写才对
- **剩余待决**：wc 的 -m 与 -L 按判定出的编码解码后统计（GBK 汉字算 1 个字符、2 个显示列），GNU 在 C 区域设置下解不出 GBK 会把字符数整个记成 0，这是按项目「文本按判定出的编码解码」的取舍，已写进 README；中文算可打印字符，所以中文文件的词数与 GNU 的 C 区域设置下不同（换 zh_CN.UTF-8 跑 GNU 就一致）；目录与缺文件的报错文案是中文、退出码是 2（GNU 是英文、1），沿用本项目约定

- **关键收获**：MSYS2 的 find.exe 会在进程启动时对参数做通配符展开（相对进程 cwd），差分对照必须把 cwd 设成空目录，否则模式会被悄悄换掉——头两轮探针的结论全是这个坑造成的假象（-name '*.txt' 明明该命中却输出为空）；GNU 的表达式语义：路径写在表达式之前，从第一个像选项的参数开始算表达式，隐式 -print 加在整条表达式后面而不是最后一个谓词后面，-prune 不算动作（所以 find . -type d -prune 仍打印命中的目录），动作恒为真且执行后不再算同层 and 链的右半边；-mmin 的精确形式把当前这一分钟算作第 1 分钟（90 秒的文件落在 -mmin 2 而不是 -mmin 1），而 -mtime 的天数计数没有这个偏移，同一个二进制里两者的口径不一致；-size 对目录恒按 0 算（Windows 的目录 st_size 会在 0 和 4096 之间跳）；-exec 找不到可执行文件时退回 cmd /c，整条命令必须作为一个参数传过去，拆开传 cmd 会按自己的编码重拼命令行，中文路径变 GBK 字节；GNU 的 %T 在 MSYS 构建里会直接 memory exhausted 崩掉，纪元秒数是 %T@，且要按整数纳秒算（浮点尾数噪声会让末几位差 1）
