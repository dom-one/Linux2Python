## 3. 已知问题与未决项

- `grep -o` 在多文件模式下不带文件名前缀，GNU 行为一致，保持现状。
- 目录操作数缺 `-r` 时的报错文案与 GNU 措辞不同，功能对，措辞后续对齐。
- 单文件搜索的 `-c` 输出不带文件名，GNU 行为一致，保持现状。
- `ls` 的空目录返回退出码 `1`（GNU 返回 `0`），是本项目「无结果返回 1」约定的刻意取舍，已写进 README。下一个指令若也属命中类，沿用同一口径。
- `ls -l` 没有链接数、属主、属组三列，也没有 `total N` 汇总行：Windows 的 `stat` 没有属主语义也没有 `st_blocks`，不是漏做。
- `cat` 的空行判定是「内容完全为空」，含空格的行不算空行（GNU 实测如此），所以 `-s` 不压它、`-b` 照样编号。
- `cat` 的二进制判定：含 NUL 字节，或 utf-8/系统首选编码/gb18030 都严格解不出来，就算二进制，按字节原样转交。latin-1 永远能解，判定文本时必须排除它。
- `cat` 的文件打不开返回退出码 2（GNU cat 返回 1），沿用本项目「用法或运行错误返回 2」的约定，已写进 README。
- `head` 的 `+N` 与 `N` 等价，不是 tail 那种「从第 N 行开始」；`-N` 才是「除末 N 行之外全要」，且 `0` 与 `-0` 含义不同。GNU 实测如此，已写进 README。
- `head` 的乘数后缀表与 GNU 帮助文本对不上（帮助说 kB=1000，实测 k=1024、kB=1000、K=1024），实现以实测为准：`b`=512、`k`/`K`=1024、`m`/`M`=1024²、`G`=1024³、`T`=1024⁴、`P`=1024⁵、`E`=1024⁶，字母加 `B` 是 1000 进制，字母加 `iB` 等同对应的单字母形式。
- `head` 的纯数字上界按 uintmax（2^64-1），负数按 intmax（2^63-1），GNU 实测如此；`Z`/`Y` 后缀语法合法但数值算出不来，报「数值超出可表示范围」。
- `head` 的打不开的文件不打标题，目录却先打标题再报「是一个目录」，两者行为不同，与 GNU 一致。
- `head` 的 `-c` 字节数按源文件算，GBK 文本输出成 UTF-8 后字节数会变多，已写进 README。
- `tail` 的 `+N` 是起点不是等价写法：`-n 5` 取末 5 行，`-n +5` 从第 5 行开始到最后。这与 head 相反（head 的 `+N` 等价 `N`），是最容易记错的一条。
- `tail` 的负号等价于正号：`-n -5` 与 `-n 5` 同义，都是取末 5 个。`-n 0` 一个不要，`-n +0` 全部都要。
- `tail` 的乘数后缀乘的是**行数**（`-n 1b` 就是 512 行），`-c` 的后缀乘的是**字节数**；两边后缀表相同（`b`=512、`k`/`K`=1024、`kB`=1000、`KiB`=`K`），GNU 实测如此。
- `tail` 的末行没有换行符时它**也算一行**（`tail -n 2` 会把它算进去），与 head 的 `-n -1` 会把它一起去掉不同。
- `tail` 回读大文件时起点多半落在行中间，开头那截半行要丢掉，所以实现要凑够「行数+1」个分隔符才停；GNU 实测同样丢半行。
- `tail` 的编码判定取的是「将要输出的那一段」而不是文件开头，所以 GBK 日志的末尾照样出中文；这是有意比 head 更进一步的取舍，已写进 README。
- `tail` 跟随时输出必须显式 flush：输出接管道时 Python 是块缓冲（攒 8KB 才写），不刷的话 `tail -f` 跟半天什么也看不见，GNU tail 跟随时是行缓冲的。
- `tail` 的 `-F`（按文件名跟）每轮重新打开再关掉文件：Windows 上打开着的文件不能改名（没开 `FILE_SHARE_DELETE`），日志轮转第一步就是改名，长期占着句柄会直接失败。
- `tail` 的 `--pid` 在 Windows 上不能用 `os.kill(pid, 0)` 探测：那边的 0 号信号会真的把目标进程终止掉，改用 `OpenProcess` 探句柄。
- `tail` 的文件打不开返回退出码 2（GNU tail 返回 1），沿用本项目「用法或运行错误返回 2」的约定，已写进 README。
- `wc` 的列宽是**逐列**算的：每列先按自己出现过的最大计数定下限；只打印一列、且不打 total 行时不做对齐，否则每列再按「普通文件字节数之和」撑开。标准输入与目录的大小事先数不出来，GNU 为它们预留 7 列。
- `wc` 的列宽是最小宽度，计数比预留宽度长时直接写长、不截断，所以 total 行的字节数可以比前面的行更宽（GNU 实测如此：`m7.txt` + stdin 的 total 是 8 位，前面的行仍是 7 位）。
- `wc` 的词：片段里夹控制字符不算断开（`a\x01b` 是一个词），整个片段里一个可打印字符都没有时不算词（纯二进制内容词数是 0）。中文算可打印字符，所以中文文件在 GNU 的 C 区域设置下词数是 0，本实现不是。
- `wc` 的 `-m` 与 `-L` 按判定出的编码解码后统计：GBK 汉字算 1 个字符、2 个显示列；GNU 在 C 区域设置下解不出 GBK，会把字符数整个记成 0，换到 zh_CN.UTF-8 跑 GNU 数字与本实现一致。
- `wc` 的 `-L` 取行内出现过的最大显示列数（`\r` 把列号清零，之后的宽度再大也不算数），不是行尾那一处的宽度。
- `wc` 的文件打不开返回退出码 2（GNU wc 返回 1），沿用本项目「用法或运行错误返回 2」的约定，已写进 README。
- `find` 的表达式优先级是 `!` > `-a` > `-o`，相邻谓词默认按 `-a` 结合；路径必须写在表达式前面，写在后面报「路径必须写在表达式前面」。
- `find` 的隐式 `-print` 加在**整条表达式**后面（不是最后一个谓词后面），且 `-prune` 不算动作（GNU 手册明确说 `-prune` 或 `-print` 之外没有动作才补 `-print`），所以 `find . -type d -prune` 仍会打印命中的目录。
- `find` 的动作会截断同层 `and` 链：`-print` 恒为真且一旦执行就不再算右半边，这是 `-name '*.txt' -print -o -name '*.md' -print` 每个文件只打印一次的原因。
- `find` 的 `-mmin` 精确形式把「当前这一分钟」算作第 1 分钟：90 秒大的文件落在 `-mmin 2` 而不是 `-mmin 1`（GNU findutils 4.10 实测），而 `-mtime` 的天数计数没有这个偏移；`-mmin +N` / `-mmin -N` 仍是自然语义（大于 N 分钟 / 小于 N 分钟）。
- `find` 的目录大小按 0 算：Windows 的目录 `st_size` 不稳定（空目录 0、条目一多就 4096），GNU 侧恒为 0；不统一的话同一条命令的结果会随目录内容变化。
- `find` 的 `-exec` 在 Windows 上找不到可执行文件时退回 `cmd /c`，且整条命令要作为**一个**参数传过去（拆成多个参数时 cmd 会按自己的编码重拼命令行，中文路径变 GBK 字节）。
- `find` 的 `-printf` 只支持 `%T@` 不支持 `%T`：GNU findutils 4.10 的 MSYS 构建遇到单独的 `%T` 会报 `memory exhausted` 崩掉。
- `tree` 的画线规则：连接符由「是不是最后一个兄弟」决定（最后一个用 `└── `，其余用 `├── `），祖先层后面还有兄弟才画竖线，否则留空；UTF-8 版竖线后面跟的是不换行空格（U+00A0）再加一个普通空格，整列 4 列宽，ASCII 版是竖线加两个空格。
- `tree` 的统计行用 GNU 的单复数写法（`1 directory` / `2 directories`），且根目录为空时连根目录自己都不计入目录数（空目录是 `0 directories, 0 files`）。
- `tree` 的 `-L N` 在上游源码里是 `Level = N-1`，所以 `-L 1` 只列根目录的直接子项且不展开子目录。
- `tree` 的 `-h` 隐含 `-s`（上游源码注释写着 Assume they also want -s）；`-t` 是旧的在前，与 `ls -t` 相反。
- `tree` 的默认排序是目录与文件混在一起按名字排，`--dirsfirst` 才分开放；GNU 用 `strcoll`（区域设置相关，UTF-8 区域设置下大小写不敏感），本实现按码位序，与本项目 `ls` 一致。
- `tree` 的 `-P` 只筛文件、目录照旧列出；某个目录命中 `-P` 时，它下面的内容全部列出（模式在该子树里失效）。
- `tree` 的通配符：`*` 不跨 `/`，`**` 跨 `/`，`|` 分隔多个候选，模式尾部带 `/` 表示只匹配目录。
- `tree` 的 `-x` 在 Windows 上按盘符判定：`st_dev` 是卷标识（C 盘与 E 盘实测不同），所以它实际是不跨盘符。
- `tree` 的操作数是文件时报「不是目录」并返回 2（GNU 是打 `  [error opening dir]` 再照常统计），沿用本项目「用法或运行错误返回 2」的约定。
- `tree` 的符号链接没法验证：Windows 上创建符号链接要管理员权限（本机报 WinError 1314），`-l` 的行为未实测。
- `find` 的 `%T@` 小数点后印 10 位（GNU 的纳秒被算大了 10 倍），且必须用整数纳秒算（`st_mtime_ns`），浮点秒的二进制噪声会让末几位差 1。
- `find` 什么都不匹配时返回退出码 1（GNU 返回 0），沿用本项目「无结果返回 1」的约定；`-delete` 这类只做动作不打印的用法按「命中了就算有结果」返回 0。
- `find` 的求值是**普通布尔短路**（tick #15 实测钉死）：动作恒为真，`-a` 左半边为假才跳右半边、左半边为真就继续算；`-o` 左半边为真就跳右半边。`-print -a -print` 打印两遍、`-print -o -print` 打印一遍。GNU 手册里「动作截断与运算链」的措辞与实测不符，**以实测为准**。
- `find` 的 `%f` 与 `-name` 按**打印出来的路径**取 basename（tick #15 实测）：操作数写 `.` 时根条目的文件名就是 `.`（不是真实目录名），写 `..` 时是 `..`，写绝对路径时才是目录名；`-name '.'` 命中根条目而 `-name '真实目录名'` 不命中。所以 basename 不能用 `fs_path.name`，要从 display 路径上取。
- `find` 的 `-exec` 的 `{}` 是**就地替换**（tick #15 实测）：`A{}B` → `A<路径>B`，`{}A{}` → `<路径>A<路径>`，两个参数各带一处 `{}` 就各换成同一个路径。`+` 形式要求 `{}` 恰好一处、单独成参数、且是最后一个，否则按用法错误处理。
- **MSYS 的 argv 改写只发生在「原生父进程 → MSYS 子程序」这条路上**（tick #15 实测）：原生 Python 直接 spawn MSYS 的 find.exe 或 printf.exe，argv 里的 `{}` 与反斜杠会被吃掉（`A{}B` → `AB`、`[%s]\n` → `[%s]n`）。⇒ 差分对照里 GNU 那一侧必须经 bash 拉起，且 `-exec` 的目标要用**原生**程序（用原生 Python 助手打印收到的 argv），否则比出来的是运行时差异而不是 find 的差异。
- **探针的「全一致」可能是假绿**：差分脚本第一版把助手脚本路径直接当可执行文件传过去，两边都「找不到这个程序」⇒ stdout 都空 ⇒ 报「37 条全一致」。判据：**候选数与输出内容都要看**，空输出不等于一致。
- **读探针结果要落盘再读**：bash 工具的输出会吃掉连续重复的内容（tick #15 里两份报告对同一条命令给出 1 个 R 与 2 个 R 的矛盾，实际两份都是 2 个 R，是读输出时被吞了一段）。核对方式是逐条比对报告文本与原始 .out 字节（脚本 `_t823_probe_find_report_audit.py`）。
- 进度文件顶部的「本次会话：cron tick #N」那一行会影响 `_t11_progress.py` 算 tick 号（它取**整个文件**里最大的 tick 号 +1，不只扫日志段）：先改标题再追加日志会多跳一号，而且正文里引用某个号也会被算进去（find 那轮写成了第 7 号又改回第 6 号，本轮正文里那句引用又把本轮算成了第 8 号，已改回第 7 号，序列才连续）。**下个 tick 要先追加日志、再改标题**，追加完再核对段号。
- `du` 的默认口径是**表观大小**（文件字节数之和，目录自身按 0 算），等价于 GNU 的 `--apparent-size`，不是 GNU 默认的磁盘占用：Windows 的 Python 拿不到 `st_blocks`，MSYS 那个 `st_blocks` 是模拟层产物（`ceil(size/512)` 再乘 1024），跟 NTFS 真实分配对不上，MSYS 侧同一个 2048 字节的文件报 4096 字节占用。
- `du` 的取整模型是「先按原始字节求和、只在显示时向上取整到块」，不是每个文件各自取整再求和：`-B 100` 下 3005 字节的目录是 31 而不是 30+1。
- `du` 的 `-t` 阈值跟**字节数**比，不跟块数比：`-t 1K` 会留下块数 1、字节数 10 的小文件（GNU 实测如此），负阈值则只留不大于它的条目（`-t -1K` 只留 1K 以内）。
- `du` 的 `-h` 尾数是**向上取整到一位小数**，取整后达到 10 就改成整数显示（10239 字节是 `10K` 不是 `9.9K`；10241 字节是 `11K`）；`--si` 是 1000 进制且单位是小写 `k`；`-h` 与 `--si` 都设置「人类可读」，命令行上靠后的那个生效（`--si -h` 是 1024 进制，`-h --si` 是 1000 进制）。
- `du` 的 `--time` 对目录给的是**子树里最新的 mtime**（含目录自身），不是目录自己的 mtime：把父目录的 mtime 设成过去、子目录设成未来，报的是子目录那个时间。
- `du` 默认把同一个文件只算一次：目录被多个操作数覆盖时，后来那份既不重复统计也不输出（`du tree tree` 只有一份输出），`-l` 才重复计入。
- `du` 的 `-s` 与 `-d N`（N ≥ 1）互相冲突（`-s` 等于 `--max-depth=0`），GNU 报冲突并退出，本实现按用法错误返回 2。
- `du` 的退出码：操作数不存在返回 2（GNU 返回 1），全被 `-t` 滤掉返回 1（GNU 返回 0）。
- **Windows 上 `os.scandir().stat()` 给的是目录枚举缓存，`st_dev` 与 `st_ino` 全是 0**：硬链接去重与 `-x` 都会失效（本轮第一版差分 43/47 组不一致就是它造成的）。要用 `os.stat()` 才拿得到真实的卷标识与文件索引。**`tree.py` 的 `-x` 有同样的问题**（它用 `item.stat()`，会把子项全滤掉），本轮按「一次只做一个命令」没动，下个 tick 可以顺手修。
- `sed` 的 `{ }` 块地址**只在进块时判一次**：GNU 把整块编译成一条命令，块里的命令改过模式空间之后块地址不再重新判定（`/bravo/{s/a/X/;t end}` 里 `t` 照样跳）。
- `sed` 的空匹配**紧跟在非空匹配后面不算一次匹配**：`s/.*/X/g` 只换一个 X，`s/x*/X/g` 换三个（空匹配之后搜索位置前进一个字符）。Python 的 `re` 不是这个规矩，差分对照时按 `re` 写会多出一串 X。
- `sed` 的 `n` 是**先打印当前模式空间再读下一行**，`N` 是把下一行接到模式空间后面；`N` 读到末尾就收工，但当前模式空间照常打印。
- `sed` 的 `s` 不带 `g` 时**整块模式空间只换第一个匹配**（`N` 拼起来的多行模式空间上，`s/\n/-/` 只换第一个换行符）。
- `sed` 的范围地址：终点是正则时**不在起始行上试**；终点永远匹配不到就**延伸到文件末尾**；起点匹配不到一行都不输出；地址 `0` 表示第一行之前（`0,/re/` 从第 1 行开始）。
- `sed` 的正则地址可以换分隔符：`/re/` 之外 `\|re|`、`%re%` 这种写法 GNU 也认。**Git Bash 里优先用这种写法**：MSYS 运行时会把以斜杠开头的参数当路径改写（`/TODO/p` 变成 `E:/software/Git/Git/TODO/p`），GNU sed 自身是 MSYS 程序所以不受影响。
- `sed` 在 Windows 上默认按**文本模式**读文件，行尾的 CR 被去掉（GNU 实测如此）；`-b` 才保留 CR。
- `sed` 的 `-i` 后缀只能**紧贴着写**（`-i.bak`），`-i .bak` 会被当成文件名（GNU 也一样）；`-i` 与 `-n` 一起用会把文件清空（GNU 实测同样如此）。
- `sed` 的退出码：脚本写错、文件读不到、目录当文件用都返回 2（GNU 分别返回 1、2、4）；正常处理完返回 0，不套用本项目「无结果返回 1」那套（GNU 也是 0）。
- **差分对照脚本要用 `-f` 传**：MSYS 运行时会把命令行里的分组反向引用吃掉（`s/(a)(l)/\2\1/` 变成 `21`），`-f` 走文件才拿得到真实脚本。
- `awk-lite` 的**分隔符分三档**（GNU awk 5.3.2 实测）：没给分隔符、或给的是单个空格 → 按**空白串**切（连续空白算一个，两端空白不算字段，空行字段数是 0）；给**单个字符** → 按**字面量**切（`.` 就是一个点不是任意字符，连续出现会切出空字段）；给**多个字符** → 按**正则**切（所以 `-F '..'` 会把每两个字符切一刀，`abcdef` 切成 4 个空字段，不是 3 个）。
- `awk-lite` 的**显式单空格分隔符等同于默认**（都按空白串切），GNU 实测如此。
- `awk-lite` 的 `{print}` **等价于 `{print $0}`**（GNU 同样接受），`print(...)` 的写法也认；多个 print 参数之间用 OFS 连接（默认一个空格，`-v OFS=;` 可改）。
- `awk-lite` 的**字段号超出范围是空串**，不报错；`$NF` 是最后一个字段。
- `awk-lite` 的**模式是正则（ERE）**，只写模式不写动作时打整行（`/ERROR/`）；`NR` 跨文件连续、`FNR` 每个文件从头算、`FILENAME` 是命令行里给的文件名。
- `awk-lite` 的 `-v` 变量放在字段位置时，**值是数字就当字段号**；不是数字就当字段名，GNU 因为没有具名字段所以给整行，本实现照抄（`-v s=b` 打在 `a b c` 上给的是整行）。
- `awk-lite` 的退出码：程序写错、文件读不到、目录当文件用都返回 2（GNU 分别返回 1、2、0——目录在 GNU 只是警告后跳过）；**正常处理完返回 0，没有输出也是 0**，不套用本项目「无结果返回 1」那套（GNU 也是 0）。
- **差分对照必须用 `awk -f` 传程序**：Windows Python 拉起 MSYS 的 `awk.exe` 时，**不含空格参数里的大括号会被 MSYS 运行时吃掉**（`{print}` 变成 `print`，gawk 报 `cmd. line:1: print ^ syntax error`），同一个程序在 Git Bash 里跑却完全正常；带空格的参数（`{print $1}`）不受影响，所以差分脚本统一走 `-f` 写文件。
- **Windows 文本模式把 `\n` 写成 `\r\n`**：跟 GNU awk 对照输出时必须先归一换行，否则每一组都显示成不一致（本轮差分第一轮 52 组全「不一致」就是这个原因，不是逻辑问题）。
- **编码判定整套逻辑**（`_detect_encoding` / `_candidate_encodings` / `_decode_sample` / `_text_score`）现在在 `cat.py`、`grep.py`、`sed.py`、`wc.py`、`awk_lite.py` 里各写了一份，属已知重复，本轮没动。
- **Git Bash 里以 `/` 开头的程序会被 MSYS 改写成路径**：`python main.py awk-lite '/^import/ {print $2}' w2l/entry.py` 里的 `/^import/ ...` 会变成 `E:/software/Git/Git/^import/ {print $2}`，本实现会明确报错（不静默算错），绕法是加 `MSYS_NO_PATHCONV=1`。

- **`cp` 的落点规则**：目标是**已存在的目录**时源落成「目录/源名」；目标**不存在**时，目标本身就是新文件/新目录（`-r` 拷目录到不存在的目标时不再套一层同名目录，`cp -r dir1 newdest` 得到 `newdest/内层文件`）。
- **`cp` 的源目录尾部斜杠不影响落点**：GNU 8.32 实测 `cp -r dir1/` 与 `cp -r dir1` 一样，都是「目标/dir1」（`rsync` 那种「拷内容」的直觉在这里不成立）。
- **`cp` 的检查顺序**：多个源时「目标不是目录」这条**先于**逐个源的存在性检查（`cp a.txt b.txt 某个文件` 报的是「目标不是目录」）；「未指定 -r」这条**先于**「目录覆盖文件」。
- **`cp` 的合并语义**：目标已有同名目录时，同名文件被覆盖、**目标多出来的文件保留**，目录本身不报错。
- **`cp -v` 只对真正动了的条目打印**：目录那行只在**被新建**时出现（合并进已有目录时不打印）；被 `-n` 跳过的文件也不打印。GNU 的目录遍历是 readdir 顺序（不确定），本实现走排序后的顺序，落地内容一致但打印顺序可能不同。
- **`cp -n` 压过 `-i`**：两个一起给时不提问，直接跳过已存在的文件（GNU 实测）。
- **`cp -u` 要求源严格更新**：mtime 相等算没更新，不复制。
- **`cp -p` / `-a` 的目录 mtime 要在内容写完之后再设**，否则被子文件的写入顶掉（文件不受影响）。
- **`cp --parents` 自己建父目录，普通递归拷贝不建**：GNU 遇到父目录不存在是直接报 `cannot create directory`，只有 `--parents` 才顺手建。
- **`cp -S` 是先把旧目标改名加后缀再写新的**（`cp -S .bak a b` 得到 `b` 是新内容、`b.bak` 是旧内容），不是写完再改名。
- **`cp` 的退出码**：出错一律返回 2（GNU 返回 1），沿用本项目「用法或运行错误返回 2」的约定；成功返回 0（不是本项目「无结果返回 1」那套）。
- **`cp -p` 的 mode 在 Windows 上落成只读属性**：Windows 没有 POSIX 权限位，`ownership`/`context`/`xattr` 接受但没有实际效果。
- **`cp` 的符号链接分支未实测**：Windows 上创建符号链接要管理员权限（本机报 WinError 1314），MSYS 的 `ln -s` 又落成普通文件，所以「默认解引用」与「-a 不解引用」两条路径都没验证过。
- **差分对照脚本要比的两个「度量坑」**：① 两个沙箱的夹具创建时刻不同，mtime 直接比数值必然假不一致，要归成「保住源时间戳 / 复制时刻」两类再比；② GNU 的目录遍历是 readdir 顺序，两个沙箱的目录项顺序天然不同，verbose 只能比**集合**不能比先后。
- **`mv` 不合并目录**（与 `cp` 最大的差异）：目标下同名目录已存在且**非空**时 GNU mv 直接报 `Directory not empty` 退出，不像 cp 那样逐个文件覆盖过去；同名目录**是空的**时移动照常进行（等于用源目录替换掉那个空目录）。Windows 的 `os.rename` 不允许覆盖已有目录，所以实现里先 `rmdir` 那个空目录再改名。
- **`mv` 的 `-i` 与 `-n` 互相清掉对方，后给的那个赢**：GNU 的 cp 与 mv 都是这个行为（`-n -i` 会提示并照搬，`-i -n` 不提示也不搬）。本项目的 cp 实现写的是「-n 压过 -i」，**与 GNU 不一致**，本轮按「一次只做一个命令」没动 cp，mv 按 GNU 走。
- **`mv` 的 `-S` 单独给就隐含开备份**（`-S .bak` 等价于 `-b -S .bak`）。
- **`mv -v` 整个目录只打印一行** `renamed 'dir1' -> 'destdir/dir1'`（不是逐个文件），带备份时同行追加 `(backup: 'b.txt~')`。
- **GNU 的 mv 不看目标文件的权限位**：只读目标照样能搬过去，Windows 的 rename 覆盖只读文件会失败，所以实现里无条件先清目标的只读属性。
- **`mv` 的 `-n` 会盖掉结构性错误**：目标同名目录非空时不给 `-n` 报「目录非空」，给了 `-n` 就静默跳过、退出码仍是 0。
- **本机文件系统的时间戳精度约 15.6ms**：同一 tick 里先后创建的两个文件 mtime 完全相同，GNU mv `-u` 判成「源没更新」就跳过 ⇒ 测 `-u` 必须用 `os.utime` 把时间戳钉死并至少隔开 1 秒。第一轮探针就是被这个坑了一次（误判 GNU mv 的 -u 不生效）。
- **跨盘的 `mv` 走「拷贝 + 删除」兜底**：同盘走 `os.replace`，遇到 `EXDEV` 才退回 `shutil.move`。
- **`chmod` 落盘只看「有没有写位」**：目标模式里 owner/group/other 三类**一个写位都没有**才设只读属性，有写位就清掉。这是 MSYS 与 GNU 一致的判据（`chmod 2`（0002）之后文件仍可写，`chmod 40`（0040）才变只读），别写成「属主写位」。
- **`chmod` 的当前模式按 MSYS 口径取**：可写文件 0644、只读文件 0444、目录 0755（目录被设成只读也仍报 0755）、可执行文件 0755、符号链接 0777。折算逻辑统一放在 `w2l/perms.py`，`ls -l` 与 `tree -p` 的权限列也用它——Windows 的 `os.stat` 合出来的是 0666/0777/0444，直接用会把组位与执行位显示错（`ls -l` 原来显示 `-rw-rw-rw-`，GNU 是 `-rw-r--r--`）。
- **`chmod` 报「打不开的文件」时，原模式沿用上一个处理过的文件**（GNU 的口径，是个跨文件的残留变量）；一个文件都没处理过时 GNU 读的是未初始化的随机值（两次跑分别是 0141 与 0155），本实现固定用 0644。
- **`chmod` 的符号模式**：复制写法（`u+g` / `g=u`）只在 `=` 时生效，`+`/`-` 配复制写法是空操作；`X` 只在「是目录」或「本来就有执行位」时才给执行位；空的权限串合法（`o=` 清空 other、`a=` 全清、`u+` 什么都不加）。
- **`chmod 644,755 f` 是非法模式**：逗号分隔的是符号模式的**子句**，不是多个模式（GNU 同此，尽管帮助文本写着 `MODE[,MODE]...`）。
- **`ls -l` 的权限列改了口径**：可写文件从 `-rw-rw-rw-` 变成 `-rw-r--r--`、目录从 `drwxrwxrwx` 变成 `drwxr-xr-x`（与 GNU 的 `ls -l` 一致）。`teach/` 里写着旧输出的教程会因此过期，教程任务下个 tick 核对时会自己发现（它每轮做全量核对）。
- **`grep` 的 `-j/--jobs` 是本项目扩展选项**（GNU grep 没有，`ugrep` 的 `--jobs` 是同一思路）：只改速度不改结果。文件列表按目录遍历顺序排好，再切成**连续**片段分给工作进程，用 `imap`（不是 `imap_unordered`）按序取回，所以并行输出与串行逐字节一致；片段数取进程数的 4 倍，让快进程能动态多领几片。文件数少于 32 时退回串行（Windows 起进程要几百毫秒）。标准输入不走并行。
- **`grep` 串行比 GNU grep 慢 1.7~2.7 倍的根因不是遍历**：E:/1（17790 个文件）遍历只占 0.317s，差在每个文件都要做编码判定——`utf-8`/`cp1252`/`gb18030`/`latin-1` 四个候选各解一遍前 8KB 再逐字符打分，纯 Python 循环。根治方向是把打分向量化或按 (文件大小, 编码) 加缓存；`-j` 只是把这份工作量摊到多核。
- **Windows Defender 会逐个扫新创建的文件**：量性能前必须预热。同一棵 912 文件的树，第一次 24.4s、第二次 0.070s；新建一棵树第一次 0.642s、第二次 0.066s。不预热就量，量到的是杀毒扫描时间（第一轮基线因此得出「比 GNU grep 慢 220 倍」的错误结论）。
- **探针里 stdout 接 PIPE 又不读 ⇒ 4KB 管道缓冲写满 ⇒ 子进程卡在写上永不退出 ⇒ 父进程死等**：症状像「实现挂死」，实际是探针自己的死锁（`_t1109` 复现：stdout 走管道就挂、走 DEVNULL 就正常）。要并发读（`communicate()`）或把 stdout 丢 DEVNULL。另外用忙等循环轮询子进程数会抢 CPU，把测量本身搞失真，要加 sleep。
