### 2026-11-19 tree.py 与项目文档的三处不一致（本轮实测）

给 `w2l/commands/tree.py` 写教程时实跑查出的。**本机没有 GNU tree**（Git Bash 里
`tree` 不是可执行命令，只有 Windows 自带的 `C:\Windows\System32\tree.com`，
那是另一个工具），所以做不了字节级差分对照，断言按上游源码规则写死
（见 `tests/test_tree.py` 的文件头）。下面三处的证据是**项目自己的文档内部自相矛盾**，
不依赖 GNU tree：

| 现象 | 文档怎么说 | 实际是什么 | 根因位置 |
|---|---|---|---|
| `-x` 把整棵树都过滤掉，只剩根目录一行 | README 第 433 行：「`-x` 实际是不跨盘符……所以 `-x` 能挡住跨盘的子目录」 | 全部条目都被跳过，输出 `0 directories, 0 files` | `w2l/commands/tree.py` 第 384 行用 `item.stat()`，第 397 行拿 `st_dev` 比对 |
| `-P` 命中目录时少展开一层 | README 第 418 行：「某个目录命中 `-P` 时它下面的内容全部列出」；源码第 221 行注释同 | 命中目录的**直接子文件**仍被筛掉，只有孙层往下才整体展开 | `w2l/commands/tree.py` 第 218~224 行：`child_active` 在读完 children 之后才算 |
| 目录联接（junction）不被认成符号链接 | 源码第 154、387 行用 `stat.S_ISLNK` 判链接 | Windows 的联接 `S_ISLNK=False`、`S_ISDIR=True`，被当普通目录无条件展开，`-l` 对它无效 | `w2l/commands/tree.py` 全篇；`-l` 只在 `entry.is_link` 为真时才改变行为 |

第一处的根因值得单独记：**Windows 上 `os.scandir()` 出来的 `DirEntry.stat()` 的
`st_dev` 与 `st_ino` 恒为 0，而 `os.stat(path)` 给的是真的卷标识与 inode**
（实测同一个文件：`DirEntry.stat()` 的 st_dev=0，`os.stat()` 的 st_dev=18303321406201763453；
st_size / st_mtime / st_mode 两边一致）。**这个坑项目里已经踩过并修好了**——
`w2l/commands/du.py` 第 391~396 行写着注释「不能用 item.stat()：Windows 上它给的是
目录枚举的缓存结果，st_dev 与 st_ino 全是 0，硬链接去重与 -x 都会失效」，
改用 `os.stat(item.path, follow_symlinks=follow)`。tree.py 没跟着改，所以 `-x` 在 tree 里是坏的。

第三处的后果实测：目录里同时有联接与它的目标时内容被列两遍；
**自引用的联接会一路递归到 64 层**，直到 Windows 的路径长度上限把 `os.scandir` 挡下来
（报「系统无法辨识文件名」，tree 以退出码 2 结束，统计行报成 `65 directories, 64 files`）。

另有 README 第 429 行的权限位说明已过期：那一行还写着「目录是 `drwxrwxrwx`、
普通文件是 `-rw-rw-rw-`」，那是 `w2l/perms.py` 落地之前的旧口径，
实际输出是 `drwxr-xr-x` 与 `-rw-r--r--`（chmod 指令那一轮把 tree.py 的权限列
改成复用 `w2l/perms.py` 之后）。

以上四处都属源码与 README 范围（开发任务），本轮按只读原则没动。

### 2026-11-22 sed.py 与 GNU sed 4.9 的三处差异、`-i` 入口缺陷（本轮实测）

给 `w2l/commands/sed.py` 写教程时，用 Git Bash 自带的 GNU sed 4.9 对拍，
查出 3 处**行为差异**，另有 1 处**真实命令行入口的缺陷**。前三处源码范围属开发任务，
本轮按只读原则没动：

| 现象 | 根因 | 位置 |
|---|---|---|

### 2026-11-23 awk-lite 与 GNU awk 5.3.2 的差异、11 个崩溃输入（本轮实测）

给 `w2l/commands/awk_lite.py` 写教程时，用 Git Bash 自带的 GNU awk 5.3.2 对拍了
82 组用例，23 组不一致。其中**一处是源码缺陷**（属开发任务，本轮按只读原则没动），
其余是实现取舍或语义分歧。

#### 一、源码缺陷：11 个输入让程序抛 Python traceback

`_format_number`（`w2l/commands/awk_lite.py` 第 443~447 行）第 445 行那句
`if number == int(number) and abs(number) < 1e16:`，在值是无穷大或 NaN 时
**先炸在 `int()` 上**（`int(inf)` 抛 OverflowError、`int(nan)` 抛 ValueError）；
而 `_to_number`（第 433~440 行）用的是 Python 的 `float()`，它接受
`inf` / `infinity` / `nan` / `1e400`。异常一路冒到 `main.py` 顶层，
用户看到的是 Python traceback，而不是本项目统一的 `错误: ...` 格式。

| 输入 | 异常 |
|---|---|
| `-v x=inf` / `INF` / `Infinity` / `-inf` / `1e400` | OverflowError |
| `-v x=nan` / `NaN` | ValueError |
| `-v n=inf '{print $n}'` / `-v n=nan '{print $n}'` | OverflowError / ValueError |
| `{print 1e400}` / `{print -inf}` | OverflowError |

GNU awk 对应的输入都不崩（`{print 1e400}` 打 `+inf`，`-v x=inf` 打 `inf`）。
另有一个不对称：`{print inf}` **不崩**，因为 `_parse_item` 先判
`_IDENT.fullmatch(piece)`——`inf` 是合法标识符，被当成变量名，报
「变量 'inf' 没有赋值」；而 `{print -inf}` 里 `-` 不是标识符字符，
落到 `_to_number` 分支才炸。

**修法方向**：`_to_number` 里用 `math.isfinite()` 判一道，无穷大与 NaN 不当数字
（或明确报错）；`_format_number` 里也加同样的保险。

#### 三、探针自己骗人：MSYS 运行时改写 argv

差分对拍第一版报出一堆「GNU awk 不认 `{print}`」的**假差异**。真相是
**GNU awk 是 MSYS 程序，原生 Windows 程序 spawn 它时，MSYS 运行时会对
未加引号的 argv 元素做花括号展开**（跟 bash 的花括号展开一个道理）：

| 传给 awk 的字符串 | awk 实际收到的 |
|---|---|
| `{print}` | `print` |
| `{print$1}` | `print$1` |
| `a{b}c` | `abc` |
| `{a,b}` | `a`（`b` 变成另一个 argv 元素） |
| `{print $1}` | `{print $1}`（原样） |

规律：**带空格的参数被 Python 的 `subprocess` 加了引号，MSYS 就不动它；
不带空格的裸参数被展开**。`MSYS_NO_PATHCONV=1` 挡不住这个（它管路径转换，
不管花括号展开）。绕法：把程序写进文件，用 `awk -f prog.awk` 传。

**对本项目无影响**：本项目是原生 Windows 程序（`python.exe`），argv 不经 MSYS
运行时，`{print}` 原样到达。**对用户有影响**：从 cmd.exe 直接调 GNU awk，
`awk "{print}" file` 的花括号会被吃掉、awk 报语法错误；同一命令在 Git Bash 里正常。
