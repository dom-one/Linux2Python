# AI/ 目录与脚本约定

`AI/` 是这个项目里专放「AI 干活时用的东西」的目录：脚本、进度文件、任务 prompt、锁文件。项目守则规定中间产物和日志一律落在 `AI/` 里，不散在根目录。

## 为什么这么创建

自动化任务会持续产生「不是项目代码、但下次还要用」的东西：进度状态、锁、tick 日志、任务说明。如果它们落在项目根目录或 `w2l/` 里，会和真正的源码混在一起——`git status` 一片脏、读者分不清哪个是产品代码、`.gitignore` 得为每种临时产物单独写规则。

所以定一个目录收拢：`AI/` 之外不落中间产物和日志（`AGENTS.md` 第 2 节）。

**为什么进度文件要「字节追加」而不是重写。** 两个 cron 任务是长期运行的，进度文件是它们的记忆。每一次 tick 都要往里写一段「这次做了什么、踩了什么坑」。如果每次重写文件：

- 历史丢失，下个 tick 无从知道上一个 tick 的负面结果（「判据误报」「产出不足」这类信息恰恰是最有价值的）。
- tick 号会退回去。`_t11_progress.py` 的 `next_tick()` 是扫描全文找最大的 `tick #N` 再加一，文件被清空后最大值是 0，下一次就又从 `tick #1` 开始，两条 tick 日志的编号会撞车。

所以写入用 `open(path, "ab")`——二进制追加模式。选二进制而不是文本模式，是因为文本模式在 Windows 上会做换行转换，写进去的字节和 `block.encode("utf-8")` 不完全一致；用二进制能保证写进去的就是编码后的原始字节，追加位置精确。

**为什么两个任务共用一把锁。** 锁保护的不是「文件内容」，而是 **Git 索引**。`git add` / `git commit` 期间会创建 `.git/index.lock`，同时提交时第二个进程会直接失败并报 `Unable to create '.git/index.lock': File exists`。开发任务和教程任务都会提交到同一个仓库，所以必须互斥。

锁还有第二个作用：避免两个任务同时改 `main` 上相邻的文件，导致合并时手工解冲突。

**为什么锁放在 `AI/锁/git.lock` 而不是系统临时目录。** 锁要跟着工作区走。放在工作区里，一眼就知道「这个工作区正被谁占着」，删掉工作区锁自然消失，不会留下系统级的孤儿锁。

## 这个文件是做什么

`AI/` 目录当前的实际内容：

| 路径 | 内容 |
|---|---|
| `AI/AGENTS.md` | 两个 cron tick 的**权威细则**：任务分工、取锁协议、进度追加格式、提交纪律、产出路径、硬红线 |
| `AI/cron-教程任务.md` | 教程任务的 prompt 真相源 |
| `AI/阅读进度.md` | 开发任务的进度（命令队列 + 已完成 + 已知问题 + tick 日志） |
| `AI/教程进度.md` | 教程任务的进度（教程清单 + 选题顺序 + tick 日志） |
| `AI/脚本/_t10_lock.py` | 工作区互斥锁 |
| `AI/脚本/_t11_progress.py` | 进度文件追加器 |
| `AI/锁/` | 锁文件目录，`acquire` 时会写 `AI/锁/git.lock` |

**一处命名不一致要注意。** `AI/AGENTS.md` 第 3、4 节引用的脚本名是 `_t10_锁.py` / `_t11_进度追加.py`（中文名），但磁盘上的实际文件名是 `_t10_lock.py` / `_t11_progress.py`（ASCII 名）。`cron.md` 和 `AI/cron-教程任务.md` 用的是 ASCII 名。**以磁盘上的实际文件名为准**——直接照 `AI/AGENTS.md` 的命令敲会报「找不到文件」。

脚本内部定位项目根目录的方式（两个脚本都一样）：

```python
ROOT = os.path.dirname(os.path.dirname(os.path.dirname(os.path.abspath(__file__))))
```

从 `AI/脚本/xxx.py` 往上退三级正好是项目根，所以在任何工作目录下执行都能算对根路径。

不负责：业务逻辑（`w2l/`）、测试（`tests/`）、对外说明（`README.md`）、教程正文（`teach/`）。

## 有什么用

- 自动任务的记忆有地方放：`AI/阅读进度.md` 和 `AI/教程进度.md` 就是两个任务的「上次做到哪」。
- 并发写 Git 有互斥保护，不用靠运气。
- tick 日志可追溯：每次做了什么、为什么做、踩了什么坑，全部留档。
- 项目根目录保持干净：根目录只有源码、配置和文档。

## 怎么用（过程教程）

### 第 1 步：看 AI/ 目录里有什么

```bash
cd E:\1\NULL\Windows-to-Linux
ls -1 AI
ls -1 AI/脚本
```

预期：

```
AGENTS.md
cron-教程任务.md
教程进度.md
锁
阅读进度.md
脚本
```

```
_t10_lock.py
_t11_progress.py
```

### 第 2 步：查锁的状态

```bash
cd E:\1\NULL\Windows-to-Linux
python AI/脚本/_t10_lock.py status
```

预期输出（没锁时）：

```json
{"locked": false}
```

有锁时输出锁文件的内容：

```json
{"owner": "开发", "acquired_ts": 1761650000.123, "released_ts": null}
```

三个字段的含义：

| 字段 | 含义 |
|---|---|
| `owner` | 谁拿的锁（`开发` / `教程` / 人工填的名字） |
| `acquired_ts` | 取锁时刻（Unix 时间戳） |
| `released_ts` | 释放时刻；`null` 表示还没释放 |

### 第 3 步：取锁

```bash
cd E:\1\NULL\Windows-to-Linux
python AI/脚本/_t10_lock.py acquire --owner 人工
```

成功时退出码 0，输出：

```json
{"ok": true, "acquired_ts": 1761650000.123, "stale_seconds": 1800}
```

失败时退出码 1，输出：

```json
{"ok": false, "reason": "锁被占用", "owner": "开发", "age_seconds": 42}
```

**拿到 `ok: false` 就不要动手。** `AI/AGENTS.md` 第 3 节写明：这种情况本 tick 不干活，直接收尾报告。

关于 `stale_seconds: 1800`：锁状态里 `released_ts` 是 `null` 且 `acquired_ts` 距今超过 30 分钟，就是**僵尸锁**（上一次任务崩了没释放），`acquire` 会直接接管它。所以「拿不到锁」最多等 30 分钟，不会永远卡住。

同一个 owner 重复 `acquire` 是允许的（代码里判断条件带了 `state.get("owner") != owner`），会重新写一次 `acquired_ts`。

### 第 4 步：释放锁

```bash
cd E:\1\NULL\Windows-to-Linux
python AI/脚本/_t10_lock.py release --owner 人工
```

成功：

```json
{"ok": true, "owner": "人工"}
```

owner 不对时：

```json
{"ok": false, "reason": "锁不属于本任务", "owner": "开发"}
```

写锁用的是「先写临时文件再 `os.replace`」的原子替换法（`write_state()` 里写 `git.lock.tmp` 再 `os.replace`），所以不会读到写了一半的 JSON。

### 第 5 步：往进度文件追加一段记录

```bash
cd E:\1\NULL\Windows-to-Linux
python AI/脚本/_t11_progress.py --进度 AI/阅读进度.md --主题 "实现 ls 指令" --理由 "命令队列里下一个" --产出 w2l/commands/ls.py --收获 "自动发现机制生效，新指令不用改主干" --负面 "无"
```

预期输出：

```
tick #1 已追加到 E:\1\NULL\Windows-to-Linux\AI\阅读进度.md
```

写进文件的是这样一段：

```markdown
#### tick #1（2026-10-28 22:30）— 实现 ls 指令
- **选本理由**：命令队列里下一个
- **产出**：w2l/commands/ls.py
- **关键收获**：自动发现机制生效，新指令不用改主干
- **负面结果**：无
```

参数说明：

| 参数 | 必填 | 作用 |
|---|---|---|
| `--进度` | 是 | 进度文件路径。相对路径按项目根解析 |
| `--主题` | 是 | 这一 tick 做了什么，一句话 |
| `--理由` | 否 | 为什么这 tick 做这件事 |
| `--产出` | 否 | 新增或修改的文件路径 |
| `--收获` | 否 | 关键收获，下个 tick 会读 |
| `--负面` | 否 | 翻车、判据误报、产出不足。**照实写**，没有就写「无」 |
| `--剩余` | 否 | 剩余待决事项，写了会多一行「剩余待决」 |

### 第 6 步：确认是追加而不是覆盖

追加前先记下文件大小：

```bash
cd E:\1\NULL\Windows-to-Linux
wc -c AI/阅读进度.md
```

追加后再看一次：

```bash
cd E:\1\NULL\Windows-to-Linux
wc -c AI/阅读进度.md
```

第二次的数字一定更大，且原来的内容还在。如果变小或内容丢了，说明用了覆盖式写法——那会让 `next_tick()` 把 tick 号退回 1。

看追加了哪些 tick：

```bash
cd E:\1\NULL\Windows-to-Linux
python main.py grep -n "tick #" AI/阅读进度.md
```

### 第 7 步：读进度文件找「上次做到哪」

开发任务读 `AI/阅读进度.md`，重点看两张表：

- **命令队列**（第 1 节）：`ls → cat → head → tail → wc → find → tree → du → sed → awk-lite`，第一个「待做」的就是下个 tick 的目标。
- **已知问题与未决项**（第 3 节）：记录了当前有意保留的行为差异，比如「`grep -o` 在多文件模式下不带文件名前缀，GNU 行为一致，保持现状」。

教程任务读 `AI/教程进度.md`，看「教程清单」表里第一个「待写」的行。

### 第 8 步：把文件写回原样

两个脚本都接受绝对路径和相对路径，相对路径按项目根解析：

```bash
cd E:\1\NULL\Windows-to-Linux
python AI/脚本/_t11_progress.py --进度 "AI/教程进度.md" --主题 "补充 grep.py 教程" --理由 "读者容易误解 BRE" --产出 "teach/07-w2l-commands-grep.py-检索实现.md" --收获 "BRE/ERE 对照表可执行" --负面 "无"
```

### 第 9 步：不要往 AI/ 里塞别的东西

`AI/` 放的是「AI 干活用的东西」：脚本、中间产物、tick 进度、任务 prompt。

不放：

- 源码（放 `w2l/`）
- 测试（放 `tests/`）
- 教程正文（放 `teach/`）
- 对外文档（放 `README.md`）
- 临时截图、下载的安装包（这些应该放到工作区之外，或者用完即删）

判断标准很简单：**这个东西下次 tick 还要用吗？** 要用就放 `AI/`；是产品的一部分就放它自己的目录。
