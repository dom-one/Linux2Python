# cron 任务与定时推进

这个项目有两个定时（cron）任务：一个持续补 Linux 常用命令，一个持续补 `teach/` 教程。这篇讲两个任务各干什么、一次 tick 按什么顺序走、进度怎么读、为什么共用一把锁。

## 为什么这么创建

**为什么分成两个任务而不是一个。** 两个任务的**写入范围完全不重叠**：

| 任务 | 能写哪些目录 | 进度文件 |
|---|---|---|
| 开发 | `w2l/`、`tests/`、`README.md` | `AI/阅读进度.md` |
| 教程 | `teach/` | `AI/教程进度.md` |

合并成一个任务的问题是：一个任务同时管「写代码」和「写文档」，它的注意力会被摊薄，两边都做得慢。而且写文档失败时（比如目录建错了）会连带影响写代码的进度记录。拆开之后每个 tick 只做一件事，产出可验证（一个提交、一次测试结果、一段进度日志）。

**为什么每个 tick 的步骤是固定顺序。** tick 是「一次最小推进」的单位。固定顺序（读守则 → 取锁 → 干活 → 测试 → 提交 → 追加进度 → 释放锁 → 报告）有两个好处：

- **可恢复。** 任何一步崩了，下个 tick 读进度文件就知道上次做到哪，不用靠记忆。
- **可检查。** 「跑测试」在「提交」之前，「提交」在「追加进度」之前——顺序本身是一种纪律，防止提交没测过的代码。

**为什么 prompt 放在文件里而不是散在调度器配置里。** 调度器里的一长串 prompt 不好维护、不好 diff、容易被改坏。所以每个任务有一份 markdown 文件作为唯一真相源：

| 任务 | prompt 真相源 |
|---|---|
| 开发 | `cron.md`（项目根目录） |
| 教程 | `AI/cron-教程任务.md` |

两份文件的抬头都写着「调度器里的 prompt 字段与本文件内容一致，本文件是唯一真相源」。

**为什么还有第三份文件 `AI/AGENTS.md`。** 两份 prompt 各写了一遍取锁命令、提交纪律、产出路径，改一处忘另一处就会打架。所以把**权威细则**抽到 `AI/AGENTS.md`，两份 prompt 只写执行顺序，并明确写了「两处冲突时以 `AI/AGENTS.md` 为准」。

## 这个文件是做什么

它讲的是「自动化怎么在这个仓库里推进工作」：

- 两个任务各自的职责边界和写入范围
- 触发时间与错峰、互斥的三层机制
- 一次 tick 的 8 个步骤
- 锁协议（取锁、释放、僵尸锁）
- 进度文件的格式和读法
- 每个 tick 结束时的报告格式

不负责：具体某条指令怎么实现（`teach/13-...`）、脚本本身的细节（`teach/15-...`）。

## 有什么用

- 人不在的时候，仓库仍然在往前推进。
- 每次推进都留下 tick 日志（做了什么、为什么、踩了什么坑），出错能回溯。
- 两个任务不会互相踩脚：写入范围不重叠，触发时间相隔 14 小时，提交时段由锁串行化。
- 想手动接管时，知道该读哪些文件、按什么顺序做。

## 怎么用（过程教程）

### 第 1 步：先读三份守则

```bash
cd E:\1\NULL\Windows-to-Linux
```

按这个顺序读：

1. `AGENTS.md` — 项目守则：目录分工、硬约束、加指令步骤、测试要求、提交要求
2. `AI/AGENTS.md` — 两个 cron tick 的权威细则：任务分工、取锁协议、进度追加格式、提交纪律、产出路径、硬红线
3. 自己负责那个任务的 prompt（`cron.md` 或 `AI/cron-教程任务.md`）

`AI/AGENTS.md` 里的硬红线值得记住：

- 开发任务不改 `w2l/`、`tests/` 之外的项目代码。
- 教程任务只写 `teach/` 下的文件，不改源码。
- 不提交没跑过测试的代码。
- 不覆盖进度文件，只能追加。
- 不把 prompt 里的示例当成现状写进文档。
- 不动 `E:\1\NULL\AGENTS.md`（上级工作区守则）。

### 第 2 步：读进度文件，确认上次做到哪

开发任务：

```bash
cd E:\1\NULL\Windows-to-Linux
python main.py grep -n "待做" AI/阅读进度.md
```

命令队列固定为：

```
ls → cat → head → tail → wc → find → tree → du → sed → awk-lite
```

本 tick 的产出范围就是队列里**第一个没做完的命令**，一次只做这一个。

教程任务：

```bash
cd E:\1\NULL\Windows-to-Linux
python main.py grep -n "待写" AI/教程进度.md
```

清单里第一个「待写」的就是本 tick 的目标。选题顺序：先补 `w2l/` 下的核心模块，再补 `tests/` 与根目录配置文件，最后补 `AI/` 与定时任务相关文件。

### 第 3 步：取锁与互斥检查

```bash
cd E:\1\NULL\Windows-to-Linux
python AI/脚本/_t10_lock.py acquire --owner 开发
```

（教程任务用 `--owner 教程`。）

四个判定，按顺序做：

1. 输出 JSON 里 `ok` 为 `false` → 另一个任务正在写本工作区，本 tick 不动手，写清锁被谁占着，直接进收尾步骤。
2. 取到锁后，先补推上一轮遗留的提交：`git push origin main`。提示没有待推送内容属正常。网络不稳导致上轮推送失败时，提交会留在本地，等这一轮补推。
3. 读对方进度文件（开发任务读 `AI/教程进度.md`，教程任务读 `AI/阅读进度.md`）末尾最近一条 tick 的时间戳。距今不足 30 分钟说明对方刚跑过、可能还在收尾，本 tick 直接收尾，不并行开工。
4. 前面三个判定都通过才往下做。

被跳过的那一轮不追加 tick 日志，只在报告里写明跳过原因——空轮次写进进度日志只会干扰下次的接力判断。

### 第 4 步：干本 tick 的活

开发任务的产出：

- `w2l/commands/<指令名>.py` —— `build_parser()` + `@command` 装饰的处理函数
- `tests/test_<指令名>.py` —— 正常路径、选项组合、错误路径各至少一条
- `README.md` —— 新指令的选项表

教程任务的产出：

- `teach/<序号>-<原文件名>-<中文短语>.md` —— 固定四个二级小节
- `teach/00-项目总览与阅读顺序.md` 的索引表里补一行（就地插入，不重写整个文件）

### 第 5 步：跑测试

```bash
cd E:\1\NULL\Windows-to-Linux
python -m pytest -q
```

`AI/AGENTS.md` 第 2 节把「跑 `python -m pytest -q`」列为固定步骤的第 4 步，位置在「提交」之前。有红就不提交。

（教程任务不写源码，但这一条对它同样适用——改了 `teach/` 之后跑一次测试，确认没碰坏别的东西。）

### 第 6 步：提交

开发任务：

```bash
cd E:\1\NULL\Windows-to-Linux
git add w2l tests README.md
git commit -m "feat(ls): 实现 ls 指令"
```

教程任务：

```bash
cd E:\1\NULL\Windows-to-Linux
git add teach AI/教程进度.md
git commit -m "docs(teach): 补充 <原文件名> 教程"
```

规矩（`AI/AGENTS.md` 第 5 节）：测试有红就不提交；一次提交一件事；提交信息 UTF-8；不改 git 全局配置；提交前确认 `git status` 里没有本次范围之外的文件。

### 第 7 步：追加进度

开发任务：

```bash
cd E:\1\NULL\Windows-to-Linux
python AI/脚本/_t11_progress.py --进度 AI/阅读进度.md --主题 "实现 ls 指令" --理由 "命令队列里下一个" --产出 "w2l/commands/ls.py" --收获 "..." --负面 "..."
```

教程任务：

```bash
cd E:\1\NULL\Windows-to-Linux
python AI/脚本/_t11_progress.py --进度 AI/教程进度.md --主题 "<原文件名> 教程" --理由 "<为什么这个 tick 写它>" --产出 "teach/<文件名>.md" --收获 "<关键收获>" --负面 "<翻车或判据误报，没有就写 无>"
```

追加完还要「把清单里当前这一项的状态就地改成完成」——进度文件的**表格**部分就地改，**历史段落**只能追加，不许重写。这两件事性质不同：表格是当前状态，历史段落是记忆。

### 第 8 步：释放锁

```bash
cd E:\1\NULL\Windows-to-Linux
python AI/脚本/_t10_lock.py release --owner 开发
```

### 第 9 步：写报告

开发任务的报告写四行：本 tick 实现了哪个命令、测试结果、新增文件路径、队列里下一个待做命令。

教程任务的报告写三行：本 tick 写了哪篇、字数与路径、清单里下一个待写文件。

### 第 10 步：确认这个 tick 算完成

`AI/AGENTS.md` 第 2 节列了完成条件：

- 开发任务：指令实现并注册、测试全绿、文档已补、提交完成、进度已追加、锁已释放。
- 教程任务：教程文件已落盘、四个小节齐全、索引表已更新、提交完成、进度已追加、锁已释放。

六条齐了才是完成态，任何一条没做，报告里写清缺哪一条。

### 第 11 步：为什么两个任务共用一把锁

因为**都要写 Git 索引**。`git add` / `git commit` 期间会创建 `.git/index.lock`，第二个进程同时提交会直接失败：

```text
fatal: Unable to create 'E:/1/NULL/Windows-to-Linux/.git/index.lock': File exists.
```

这不是「内容冲突」，是文件系统层面的互斥，没法靠 merge 解决，只能靠事先排队。锁把两个 tick 的「提交」这一小段串行化。

第二个作用：两个任务同时改 `main` 上相邻的文件时，即使没撞索引锁，也会产生需要人工解的冲突。

锁的状态存在 `AI/锁/git.lock`（`owner` / `acquired_ts` / `released_ts`）。`released_ts` 为 `null` 且 `acquired_ts` 距今超过 30 分钟 = 僵尸锁，`acquire` 会直接接管，不会永远卡住。

### 第 12 步：当前状态

两个进度文件的抬头记着各自的当前轮次与下一步：

```
最后更新：2026-10-28
本次会话：cron tick #1（首次铺开，已完成 17 篇）
```

教程任务已经跑过 tick #1（17 篇教程一次铺开），开发任务的命令队列第 1 项（`ls`）还是「待做」。

进度文件的 tick 日志区只有一句引导语：

> ## 4. tick 日志
>
> 以下段落由 `AI/脚本/_t11_progress.py` 追加，历史不重写。

之后每次 tick 会在这个引导语下面追加一段 `#### tick #N（时间）— 主题` 的记录。

### 第 13 步：手动模拟一次 tick

不接调度器也能手动走一遍完整流程（提交那步按需跳过）：

```bash
cd E:\1\NULL\Windows-to-Linux
python AI/脚本/_t10_lock.py acquire --owner 人工
python main.py
python -m pytest -q
python AI/脚本/_t11_progress.py --进度 AI/阅读进度.md --主题 "手工验证流程" --理由 "熟悉 tick 流程" --产出 "无" --收获 "流程跑通" --负面 "无"
python AI/脚本/_t10_lock.py release --owner 人工
```

跑完检查锁已释放：

```bash
cd E:\1\NULL\Windows-to-Linux
python AI/脚本/_t10_lock.py status
```

预期：

```json
{"owner": "人工", "acquired_ts": ..., "released_ts": ...}
```

`released_ts` 不再是 `null`，说明释放成功。

### 第 14 步：两个任务怎么错峰

两个任务不并行，靠三层机制叠着保证：

| 层 | 机制 | 作用 |
|---|---|---|
| 1 | 时间错峰 | 开发每天 02:00，教程每天 16:00，相隔 14 小时，调度层面就不撞 |
| 2 | 共享锁 | 都写 git 索引，共用 `AI/锁/git.lock`，取锁失败即跳过，不排队不重试 |
| 3 | 活动窗口 | 取到锁后再看对方进度文件末尾最近一条 tick，30 分钟内说明对方刚跑过，本轮跳过 |

每日一次也是配额上的必要选择：AI 有每五小时限额，任务越密越容易撞线；一天两轮（开发 + 教程）留出的余量足够。

### 第 15 步：脚本名以磁盘为准

脚本的实际文件名是 `AI/脚本/_t10_lock.py` 与 `AI/脚本/_t11_progress.py`（ASCII 名）。`AI/AGENTS.md`、`cron.md`、`AI/cron-教程任务.md` 三处用的都是这两个名字。

**以磁盘上的实际文件名为准。**
